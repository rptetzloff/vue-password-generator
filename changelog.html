v3.4.0
2026-08-16
Security
The page can no longer build code from a string
The security policy stopped allowing unsafe-eval, and the Vue build that shipped with a compiler in it is gone — so it is not merely disallowed, it is impossible.
Security
  • unsafe-eval is out of the Content-Security-Policy. It had been there since the beginning and was genuinely required: components declared their markup as strings, and Vue compiled those in your browser through new Function. Without the allowance every page rendered blank — measured, not assumed. It was the weakest line in an otherwise strict policy.
  • And the compiler is gone with it, which is the stronger half. The page now ships Vue's runtime-only build, 88 KB against 146, with no template compiler in it at all. The allowance is not just withdrawn but unnecessary: nothing on this origin can build a function from a string, whatever the policy says.
  • Two guards so it cannot come back quietly. A component reintroducing a runtime template would need both the compiler and the allowance again, and its failure mode is a blank page rather than an error — so a test fails instead, naming the file. A second test fails if either entry point stops importing the runtime-only build.
Improved
  • Markup lives in files you can open. The two largest source files were roughly half HTML by line, embedded in JavaScript string literals. That markup is now thirteen .html files under src/templates/, with editor support and syntax highlighting like any other HTML. main.js goes from 2,948 lines to 1,498 and vault-app.js from 2,687 to 1,518; the vault's single template was 1,168 lines on its own.
  • Nothing compiles in your browser any more, so the work of turning templates into render functions — previously done on every page load, in front of you — happens once, before release.
Added
  • A build step, and the smallest one that would do. It compiles templates and does nothing else: no bundling, no minifying, no transpiling, no rewriting of imports beyond pointing them at the vendored Vue. Its output is committed, so a server still sends exactly what is in the repository and there is no pipeline in between.
  • Both halves are committed and a test keeps them honest. The generated code is legible but nobody would choose to read _hoisted_47; the template beside it is what a person reads. So the templates stay in the repository too, and a test recompiles every one of them and fails if the committed output has drifted — the same treatment the policy's script hashes already get.
Known limits
  • It is not smaller, despite the smaller Vue. Compiled render functions are bigger than the markup they replace: 198 KB more code against 58 KB less compiler. Compressed, which is how it actually travels, that nets out to roughly 7 KB saved — a wash. The reasons for doing it are the policy and the extension path, not the byte count, and an earlier claim of a 58 KB saving counted only the half that helped.
  • The project now has a development dependency, which it has not had since Vite was removed. Nothing is fetched to run the site — runtime dependencies are still zero — but building the templates needs Vue's compiler, and contributors need npm ci to regenerate them or run that one test. The browser build of the compiler cannot do it: it refuses the mode that emits modules, and the mode it will do emits code that is illegal inside one.
  • style-src still allows unsafe-inline. Hashes do not cover style attributes and the documentation page carries 123 of them. With images and connections locked to this origin the usual CSS exfiltration trick has nowhere to send anything, so this is the cheaper half of the same trade — but it is still a weakening, and it is still there.
v3.3.0
2026-08-15
Feature
Bring your own cloud
The vault can live as a file in a folder you choose — so the folder you already sync carries it between machines, with no account and nothing of ours in the middle.
Added
  • A vault that lives in a folder you chose. Point it at a directory and the vault becomes one encrypted file there. If that directory is one your computer already syncs — Dropbox, OneDrive, iCloud Drive — then your vault is carried between machines and backed up by software you already trust. Your provider learns that a file changed and roughly how big it is; it never learns what is in it, because it cannot. Chromium desktop only, and see Known limits below for why that is not a matter of waiting.
  • Moving is copy, verify, switch, clear — in that order, and never a move. The verify is a read-back, because a full disk, a read-only folder and a sync client rejecting a file all look like a successful write until you look again. If any step fails the original is still where it was. A folder that already holds a vault is refused rather than overwritten.
  • Open a vault that is already in a folder, which is how a second computer joins. It requires a vault to be there, writes nothing at all, and only records where to look. Deliberately a separate button from Move rather than one that guesses: a control whose destructive behaviour depends on what it happens to find is fine until the day it is not.
  • Two computers can share one folder. Saving reads what is in the folder first and merges rather than overwriting, so entries added on either machine survive and a deletion made on one is not resurrected by the other still holding the entry. This also fixes two tabs of one browser, which is the same lost update over a shorter distance and rather more common, since nothing tells you the vault is open twice.
  • When you both changed the same entry, it asks. The save stops, nothing is written, and you get the fields that differ side by side with keep mine, keep theirs, or keep both. It asks because it cannot know: timestamps say which was saved last, not which knew more, and an edit box open in one browser holds a copy from before the other browser saved. Deleting on one device while the other has the entry open is the same question with different wording.
  • Stop using it here — the missing third option. Delete removes the file for everyone sharing the folder; moving it back takes it away from them; neither is "I am done with this vault on this computer". This forgets the folder and the local draft, locks what is open, and touches the folder not at all. No passphrase, because nothing is destroyed. It is also the only exit from the screen you get when a folder is gone for good.
  • A list of your recent backups, inside the vault rather than beside it: the last five, each with when it was made, how many entries the vault held at the time, and which browser made it. Every machine that opens the vault sees the same history — a backup made in Chrome is no longer reported as missing by Edge.
  • Pick the generator at the box you are filling. Generate is a split button now, on every secret field: the left half runs whatever is in use and names it, the arrow opens the list. Choosing a generator for a security answer used to mean scrolling up to the password field, changing it there, and scrolling back.
  • HSTS, two years and including subdomains, so a first visit typed without https:// cannot be answered by something other than us. Deliberately without preload, which is close to irreversible and deserves its own decision.
Improved
  • The vault now knows its own name. Inside the envelope was a bare list of entries, with nowhere to record a fact about the vault as opposed to its contents. It now carries an id, so two copies can establish they are the same vault before reconciling, and a note of which device wrote last. Versioned separately from the envelope, since one is what the ciphertext holds and the other is how it is wrapped. A vault written before today loads unchanged and gains an id the first time it is opened.
  • A configured folder that cannot be read is never reported as an absent vault. Browsers forget folder access after a restart; drives unmount and directories get renamed. The dangerous answer in every one of those cases is "no vault found, create one?", because someone will say yes and the first save writes an empty vault over the top. It gets its own screen instead, saying the vault is not lost, with a Reconnect button.
  • A refused save leaves the list exactly as storage has it. Anything else means a saved-looking row that is on no disk anywhere, which some later save would write after all. What you typed stays in the editor, because the refusal stops before the dialog closes.
  • The persistence warning tells the truth in both modes. It was telling people with a vault in Dropbox that "there is no copy of this anywhere else". In folder mode what is at risk is the pointer, not the vault: lose this browser's storage and the file is still there, this browser just forgets where.
Fixed
  • The conflict dialog showed a secret that is shown nowhere else. Found in a security review of this release, in code written the same day. The table of differing fields stringified anything object-shaped, and the one-time code object puts its seed first — so the row opened with the raw TOTP seed in clear text. It appears nowhere else in WordLock: the editor shows only "Code set for issuer (account)", the list shows only the six digits derived from it. Custom fields marked secret printed their values too. Secrets are now masked with a reveal, and the one-time code seed has no reveal at all, because unlike a password it does not rotate when you change the password. The comparison still runs on the real values, so a changed seed is still reported as changed — it is only the display that is redacted.
  • Deleting a vault let go of nothing. Delete a folder vault in Chrome, create a new one in the same folder from Edge, and Chrome announced a vault ready to open: somebody else's, with a passphrase it had never been given. Worse in the other direction, since a browser still aimed at that folder would write a new vault into it. Deleting now releases the folder too.
  • Opening a folder vault left the page on "create a vault" until you navigated away and came back, because the initial read returns early once it has run — right for a page load, wrong when the storage changes underneath.
  • The backup reminder was per-browser, so Edge reported a vault as never exported an hour after Chrome had exported it. The record was in this browser's storage; it is a fact about the vault and now lives in it.
  • "There is no vault in that folder" now says what it found. True and useless when the folder plainly has things in it. Dropping a backup file in and pointing at it gets its own answer, since that is a reasonable thing to try and the response someone needs is not "no vault" but "that is a snapshot to restore through Import".
Known limits
  • Firefox and Safari cannot do this, and it is not a matter of waiting. Reading a file you pick works everywhere — that is what Import uses. Writing back to it needs the File System Access API, which neither has implemented; Mozilla's published position on the folder and file pickers is harmful, while its position on the sandboxed origin-private filesystem is positive. The objection is precisely to the part this needs. A replica that cannot save is a viewer, not a replica.
  • Merging cannot see across your cloud provider's own sync. Two machines saving while the folder is out of step — offline, or inside the seconds your client takes to catch up — produces a conflicted copy file, which is Dropbox's arbitration and invisible to this page. Import that file and its entries merge back in.
  • Simultaneous saves are still not safe. The window between reading the folder and writing to it is now milliseconds rather than a whole session, but it is not zero.
v3.2.0

Minor
Fifteen seconds to change your mind
Deleting an entry is now undoable for a few seconds — and underneath it, the entry model learned to survive being copied to a second device.
Added
  • Undo, for fifteen seconds after a delete. A toast counts down from fifteen with Undo and Delete permanently beside it, and the modal confirmation that used to sit in front of every deletion is gone — the undo is the confirmation, and unlike a dialog it does not interrupt someone who meant it.
  • The deletion is not deferred, which is the part worth knowing. The entry is removed and written to disk before the toast appears. Close the tab, reload, lock the vault or lose power during the countdown and it stays deleted, because otherwise the word does not mean anything. What the window buys is an undo, not a delay. Leaving the page forfeits the undo; it does not cancel the deletion.
  • And the copy that makes undo possible is treated as what it is — a plaintext password living slightly longer than you asked. It is held in memory only, never written; fifteen seconds rather than sixty; Delete permanently drops it early; and it is discarded the instant the vault locks, including by the idle timer.
Improved
  • The vault can now survive being copied to a second device. Nothing syncs yet and no transport exists — this is the entry model any of that would need, built while there is exactly one client and the migration is free. Every entry carries an updatedAt, deletions leave a marker rather than a hole, and reconciling two copies is a real operation rather than a hopeful one.
  • The bug it exists to prevent. Deletions were plain removals, and the import merge is non-destructive by design — correct for importing someone else’s file, catastrophic for two copies of your own. Delete an entry on the laptop, sync from the phone, and the merge hands it straight back. Silently, and specifically for the entries you most wanted gone. A deletion now leaves a tombstone: an id and a time of death, carrying no password and no label, since a label is information too.
  • Reconciling replicas is deliberately not the same code as importing. An import must never delete; a replica merge must. Collapsing the two would mean a malformed CSV could carry a delete instruction, and there is a test that fails if anyone tries. Last-writer-wins per entry, which is the honest floor rather than the ideal: two edits between syncs means one loses, and nothing can know which was wanted — but the loser is one entry’s fields, never the vault and never a silent deletion.
  • Deletion markers are reaped after ninety days, because a marker that lives forever is a slow leak of what the vault used to contain. Far longer than any plausible gap between two devices, and the cost of being wrong is one resurrected entry rather than one lost, which is the right direction to fail in.
v3.1.0
2026-08-14
Minor
A way back in
Forgetting the passphrase used to end the story. A recovery key is a second key that you hold — not a back door that we do.
Added
  • A recovery key, for the one failure a backup cannot touch. Sixteen words, generated here, shown exactly once. A backup protects the data; a recovery key protects access, and a backup you cannot decrypt is as lost as no backup at all. The two are complements and you want both — a recovery key does nothing for a vault that was never exported and no longer exists, and a backup does nothing for a passphrase nobody remembers. Offered right after the vault is created, where someone is already thinking about losing access, and from settings after that; nobody goes hunting in settings for a feature they do not know exists.
  • Generated, never chosen, and that restraint is the whole security argument. There is deliberately no way to supply your own phrase. A vault with two keys is only as strong as the weaker one, because an attacker takes whichever is cheaper to break — so a memorable recovery phrase would quietly become the real strength of your vault no matter how good the passphrase was. At 225 bits, drawn from the same 17,576-word list the Words generator uses, the recovery path is not attackable at all and the passphrase stays the binding constraint. Between those two positions is a trap: anything memorable is anything guessable. Words rather than base32 because this gets written on paper and typed back by hand months later, and duplicates are allowed, because independent draws are exactly what make the bit count true.
  • Shown once, and there is no screen that shows it again. The vault holds your master key encrypted under those words, which is not the same as keeping them — so there is nothing to show. Lose it and you generate another, which retires the previous one the moment it is made. The dialog gates its own dismissal behind a written-it-down checkbox, offers copy and download, and says plainly that anyone holding the words can read every password in the vault.
  • Recovering is one operation, not two. The key and the new passphrase are asked for together, so the vault is never sitting open with no passphrase anyone knows. It re-seals under a brand new master key, which means the forgotten passphrase stops working too — whoever might have learned it is locked out along with your memory of it. The key is spent by using it, having just been typed onto a screen and possibly read aloud. The lock screen checks the words as you type, so “that is 15 words” and “brambel is not one of the words” arrive before a million PBKDF2 rounds rather than after.
  • Adding or removing one requires the passphrase, even with the vault already open. An unlocked tab proves a tab is open, not who is asking, and minting a permanent second key to someone’s vault is not something a passer-by should manage. The same rule already guarded deleting a vault.
Security
  • The vault envelope is versioned, and v2 wraps a master key. v1 encrypted the entries directly under the passphrase-derived key, which leaves nowhere to put a second way in: the alternatives were storing the passphrase somewhere, or keeping two full copies of the ciphertext in step. v2 encrypts the data under a random master key and wraps that key once per slot. Two dividends that were not the reason for it: changing the passphrase now re-wraps 32 bytes instead of re-encrypting the whole vault, and revoking recovery is deleting one field. The master key is generated extractable, because wrapKey will not export a key that is not, and immediately re-imported non-extractable for use — what the page holds still cannot be read out by script.
  • Existing vaults are untouched until you ask for something. A pre-v2 vault keeps opening exactly as it did and converts only when a recovery key is added or the passphrase is changed, both moments where the passphrase is already in hand. No vault is silently re-encrypted during what the user thinks is an unlock.
  • “There is no recovery” was true and is now not. That sentence appeared on the create screen, in the docs, on Legal and in the adopt-a-passphrase warning, and a claim this product makes about itself does not get quietly deleted when it stops holding. All four now say what is actually true: there is no account and no server, so there is nothing for us to reset — and a recovery key is a second key you hold, generated in your browser, never transmitted, never seen by us. Lose both and the vault stays closed, which is still the design rather than a shortcoming.
Fixed
  • The Add button was the same colour as the page behind it. --primary is both the page gradient’s first stop and the primary button’s fill, and the vault bar sits on the band rather than in a card, so in light mode the button was rgb(3,105,161) on rgb(3,105,161): 1.00:1, with only its white label visible. Dark measured 1.59:1 — less obvious, equally under the 3:1 WCAG 1.4.11 asks of a control’s boundary. Every existing check passed, because they all compare the pair the design intends: --on-primary on --primary is 5.93:1. The pair that mattered was one nobody compares, because those two colours are not meant to meet. The bar’s controls now use the --band-control-* tokens the header and footer already had.
  • The recovery dialog opened underneath the fixed header. It shares the entry editor’s backdrop, whose insets are measured on open — but only from the editor’s own watcher, so this dialog inherited whatever the editor last left behind, or nothing at all if the editor had never been opened. Now measured for both, with the page behind it locked.

Patch
Stop serving yesterday's build forever
The service worker answered every request from its cache and never asked the network again. A vault you cannot update is a vault whose next fix never arrives.
Fixed
  • The update path did not update. Every request was answered from the cache and the network was never consulted again. The design assumed each release renames the cache by bumping the version — true in principle, and four releases went out without one, at which point anyone who had loaded the site was pinned to that build with no way forward. Not stale until the next release: stale permanently, and silently. On a password manager that is more than an annoyance, because it means a fix for a real bug never reaches the people running the version that has it. Page loads now try the network first and fall back to the cache, so a deploy is visible on the next load; everything else is stale-while-revalidate, answering instantly from cache while fetching a fresh copy for next time. Offline is unaffected either way — a failed fetch simply uses what is already there. ignoreSearch is now scoped to the navigation fallback alone, because applying it to every request also defeated ?v= cache-busting, which was the only manual escape left.
  • And a second, unrelated cause of the same symptom, local only. The dev server sends an ETag and no Cache-Control at all, and with no stated freshness a browser may reuse what it has without ever asking. That is what made an edited stylesheet need a hard refresh, repeatedly. It was never the service worker: every page skips registration on localhost. A serve.json at the repository root sets no-store, measured before and after across CSS, JavaScript, HTML and JSON. Render reads render.yaml, so the file changes nothing in production.
v3.0.0
2026-08-14
Major
The vault — somewhere for a password to go
A generator was a moment-tool: you took a password and left, and the clipboard timer erased the only copy thirty seconds later. WordLock now has an encrypted, offline, accountless vault to keep it in — and a way back out again. The generator stays first-class and stays the front door; that is a condition of the change, not a courtesy.
Added — The vault
  • An encrypted local vault at /vault.html — entries sealed as a single AES-256-GCM blob under a key derived from a passphrase you choose, PBKDF2-SHA256 at 1,000,000 iterations, comfortably clear of OWASP’s 600,000 floor. No account, no server, no sync, and no recovery: nobody can open it or reset the passphrase, including us. The iteration count travels inside each vault, so raising the default later will never strand an older one.
  • Keep beside every generated password, and on every history row — files it in the vault with a label, the date, and the exact entropy the generator computed at the time, shown afterwards as a coloured pill so a weak old entry is visible at a glance.
  • Auto-lock on idle, with the window in the same settings gear as the clipboard timer (Never, 1, 5, 15 or 60 minutes; 15 by default). Locked means the key has been discarded, not hidden. The deadline is measured against the clock rather than trusted to a timer, so a laptop that slept through it locks on waking.
  • Generate straight into a vault field. Every password field, and every security answer, has a Generate button and a picker for which of the seven generators to use — running that generator with its own current settings, so there is one place to configure Words and it is the Words tab. Making this possible meant lifting the seven generators out of main.js, where each lived as a closure inside a Vue component that nothing else could call. The alternative was a second copy of the generation logic, which is how two code paths end up disagreeing about entropy — the one number this site cannot afford to get wrong. The figure now comes back with the password, so an entry created here carries the same exact bits as one filed with Keep, because it is the same code. main.js is 526 lines lighter; verified by capturing all seven entropy breakdowns before and after, five of which are bit-for-bit identical and two of which differ only in the random draw.
  • Groups and sorting. A free-text group on each entry — not a managed folder tree, because a vault of a few dozen entries does not need a taxonomy and the cost of one is that every new entry becomes a filing decision. Existing groups are suggested as you type, the list renders under group headings with Ungrouped last, and a filter narrows to one group. The group picker is a list of checkboxes, so several groups can be shown at once, and ticking none means all rather than nothing. Four sort orders: newest, oldest, by name, and weakest-first for auditing — plus a Group them toggle, because grouping and auditing pull in opposite directions. With grouping on, weakest-first means weakest within each group, so a four-entry vault at 128/56/26/56 bits lists as 56, 128, 26, 56; flat it lists as 26, 56, 56, 128. The first is right for finding an entry you know about and the second for finding the one you should fix, and no default serves both. Entries with no recorded entropy sort to the bottom of weakest-first rather than the top — an unknown figure is not evidence of a weak password, and leading with the unknowns would bury the ones worth changing. Groups survive export and import, including from other managers, whose folder column goes by at least four different names.
  • Tags, which are not a second name for groups. A group is one dimension — an entry lives in exactly one, the way a sheet of paper is in exactly one drawer. Tags are as many as you like, and the company credit card really is both Work and Finance. Type to add, pick from the ones already in use, and click a tag on any entry to filter to it. Stored lower-cased with whitespace collapsed and duplicates dropped, so Work and work are one tag rather than two that look identical in a list. The filter menu is deliberately the same widget as the group menu running the opposite operator: ticking two groups shows entries in either, because an entry has one group and and would always return nothing; ticking two tags shows entries with both. Getting that backwards makes tags feel broken in a way nobody can quite name, so the menu states it above the list. Tags survive the encrypted backup and the JSON export intact and get a column of their own in the CSV — space-separated, which is what 1Password and Bitwarden read — and an import recognises tags, tag and labels.
  • One-time codes, and the warning they ship with. Paste an otpauth:// link or a base32 secret and the entry shows a live code with its countdown. RFC 6238 over the browser's own HMAC — no dependency — checked against the test vectors published in the RFC itself for SHA-1, SHA-256 and SHA-512, rather than against another implementation of the same guesswork. Two warnings sit above the input, unmissable and uncollapsed, because they are the reasons to hesitate and belong before the secret is pasted rather than after. First: lose this vault and you are locked out of the account. The seed lives only here, so an unbacked-up vault takes the password and the second factor together — which is precisely the situation the second factor exists to survive. Second: a one-time code is a second factor only while it is kept apart from the first. Storing the seed beside the password means whoever opens the vault has both. It is still a real gain against a password leaked at the site's end, which is the common case, and it is the trade every password manager offering this makes quietly — the difference here is that it is said out loud.
  • Web addresses can be named. One login routinely covers several hosts that are not interchangeable — the site, its admin panel, the staging copy, the store listing — and a bare list made you read hostnames to tell which was which. Each address takes an optional name now, shown in place of the host: Main, Dev, Store. Addresses saved before this, and every URL any other manager exports, still load: a plain string arrives as an unnamed address rather than as nothing.
  • Rows carry text labels. Password, User and One-time are written out rather than left to an icon. On a card holding a password, a username, a rotating code, two custom fields and three named links, icons stop being self-evident.
  • The password row stops crushing itself. At narrow card widths the value was squeezed to a sliver to keep five icon buttons on one line, and with word-break: break-all that rendered the password as a single vertical column of bullets, one per line. The value keeps a floor now and the buttons drop below it — driven by a container query on the card rather than a viewport media query, because the card is narrower than the window by the page gutters and narrower again inside a group, so a 480px breakpoint never fired while the password was already unreadable.
  • Editing happens in a dialog now, not at the bottom of the page. The editor used to be a card appended after the list — fine at two entries, absurd at two hundred, since editing the first meant scrolling past every other to reach the form and again to get back. Escape closes, Tab stays inside, focus lands in the first field, the list behind stops scrolling, and Save and Cancel are pinned. Clicking the backdrop closes it, so it compares against a snapshot taken on open and asks before discarding real changes. It is inset between the header and the floating nav rather than covering them, which needed the bars' edges rather than their heights — the nav floats clear of the bottom, so its 45px height was 12px short of the gap it needed — and re-measured on resize, since the header condenses to 45px, 71px or 95px depending on width and scroll.
  • Each secret reveals on its own. One flag per entry meant unmasking the password also unmasked every security answer and every secret field at once; reading one aloud put the rest on screen, which is the opposite of what masking is for. Every secret has its own eye now, with a reveal-all on the card for when you do want the lot.
  • A half-finished entry survives the trip to the generator. Following Change settings used to discard whatever had been typed, which made the link a trap. The draft is now kept and restored when you come back, and the generator shows a way back to it. It contains a password, so it is sealed with the vault's own key and stored as ciphertext rather than dropped into sessionStorage — which would have been four lines and a plaintext secret at rest for as long as the tab lived. A draft sealed under a passphrase you have since changed is discarded rather than blocking the vault, and it is cleared on save, on cancel, and when the vault is destroyed.
  • Generator tabs are addressable. /#words opens Words, and the vault's Change settings link now goes to the generator it is actually set to use rather than to whichever tab happened to be open last. Switching tabs keeps the hash in step via replaceState, so a tab is bookmarkable without filling the back button — measured at zero history entries added across three switches. No router: one id, one hash, one lookup, and a test that fails if the tab list and the generator list ever disagree.
  • Custom fields on an entry. Named name/value pairs for whatever an account actually needs — a second login, a PIN, a customer number. The request was "a second password or username", and that answer runs out at the next account; a named pair does not. Mark one secret and it gets the password treatment: masked, copied through the clipboard timer, generatable. Leave it plain and it stays readable, because hiding a customer number behind dots helps nobody.
  • Groups and entries collapse. Chevrons on both, plus Collapse all, so a long vault can be skimmed as a list of labels instead of a wall of rows. A collapsed entry still shows its username, which is the one thing that tells two logins on the same site apart. Collapsed state is stored as the set of things closed, so anything newly added arrives open — remembering what was open makes every new entry appear folded, which reads as a failed save.
  • Reused passwords are found and flagged. A badge on each affected entry naming how many others share its password, a summary above the list, a filter to show only those, and a warning while editing — before the password is filed under a second name — that names what it collides with. Reuse is the failure that turns one breach into several: the site that leaks your password is rarely the one you cared about, and it hands over the one you did. It is also the only password health a local vault can assess with certainty, so it is the only kind offered; the remote sort, asking a service whether your passwords appear in a breach corpus, stays on the permanent no list. Exact matches only — Password1 and password1 are two passwords, and flagging a near-miss would be a guess presented as a finding.
  • Full entries, not just strings — username, any number of web addresses, and security question/answer pairs. Answers are treated as the secrets they are: masked, copyable, and covered by the clipboard timer, with the reminder that they need not be true. Search covers labels, usernames, notes and addresses.
  • Persistent storage is requested, the answer is shown, and it is now actionable. The first version stated the risk and offered nothing to do about it, which is the least useful shape a warning can take. It now reads the permission state and gives advice that fits: Chrome and Edge never ask, they decide — granting it once a site is installed, bookmarked or used enough, and reporting denied until then, so "denied" usually means "not yet". Installing is the reliable fix and it says so. Firefox does prompt, and there the Ask again button is the request. It also shows the vault's size against the space available (typically tens of kilobytes against gigabytes) so the risk can be judged rather than merely feared, re-checks on every visit since the grant can arrive later, and still says plainly that none of it substitutes for a backup — a promise not to evict is no protection against a lost laptop or your own hand on Clear browsing data.
Added — Getting your data out
  • Encrypted backup — the sealed vault as a single .json file, still encrypted, safe to keep anywhere, restorable with the passphrase it was made with. This is also the sync story, deliberately: you move the file, and no server ever holds the ciphertext.
  • Plain-text export, reversing an earlier decision. The roadmap said plain-text export would not be offered, on the grounds that a CSV of passwords is the format every manager regrets supporting. That reasoning was right about the format and wrong about the alternative: refusing every exit but "another copy of WordLock" is lock-in, and an escape hatch you cannot use is not an escape hatch — particularly with no account behind the product to recover anyone who gets stuck. JSON and CSV both ship, behind a confirmation that says exactly what the file is, with PLAINTEXT in the filename and a warning inside the JSON itself. Only the encrypted backup counts as a backup.
  • Import that merges and never deletes. Reads WordLock backups, WordLock plain exports, and CSVs from other managers — the common Bitwarden, LastPass and 1Password header names are recognised. Entries already present are skipped, so restoring an old backup cannot silently wipe newer work. Identity is the entry id where both sides have one and the password paired with its label otherwise, because two accounts can share a password and one account's password can change.
  • A quiet backup reminder — one line of text noting how many entries have been added since the last backup, and a link to make one. Not a modal: a vault that shouts at every visit gets ignored at the visit that matters.
Security
  • A passphrase on the worst-passwords list is refused, not merely scored badly. 515 entries compiled offline from the SecLists (MIT) "500 worst passwords" plus curated additions, shipped with the site — nothing you type is ever sent anywhere to be checked. Against a vault this is not a weak key, it is no key, so the create and rekey forms reject it outright. On the generator's strength readout such a password now reads zero bits. In practice this changes the number far more than the verdict: 497 of the 499 tested already rated weak.
  • Live passphrase strength, labelled as a ceiling rather than a score. The vault forms show at most N bits as you type, with the deductions named. Everywhere else on the site the entropy figure is exact, because the generator made every random choice and can count them; it cannot know what went into something you typed, and a real attacker's dictionary knows words, names and dates that a few hundred lines of arithmetic do not. The reading can say a passphrase is bad and never that one is good, and the wording says so.
  • A Content-Security-Policy. For a vault with no server, the directive that earns its keep is connect-src 'self': whatever runs on this origin, it has nowhere to send what it finds. form-action 'none', img-src 'self' and base-uri 'none' close the other classic exfiltration routes, and every inline script is allowed by hash rather than by 'unsafe-inline'. 'unsafe-eval' had to stay — components are declared with Vue's template: option, so Vue compiles them at runtime via new Function, and without it every page renders blank; that was measured rather than assumed, and dropping it needs a build step. The hashes are not hand-maintained: test/csp.test.js recomputes them from the HTML and fails on drift, because a stale hash is a blank site. It also normalises line endings first — the working tree is CRLF and git stores LF, so hashes computed the obvious way pass locally and break in production.
  • PBKDF2 iterations raised to 1,000,000 from OWASP's 600,000 floor — and deliberately not to ten million. Measured at ~0.1ms per thousand iterations: 600k is 54ms, 1M is 93ms, 10M is 1032ms. Attacker cost is linear, so 600k → 10M is 16.7×, which is 4.1 bits — less than one extra random lowercase letter — bought with a second of unlock latency on a fast desktop and several on a phone. Adding one word to your passphrase beats the whole trade and costs nothing. The bump is about staying clear of the floor as hardware improves, not about the bits. Existing vaults carry their own iteration count and keep opening; changing the passphrase re-encrypts at the new one.
  • Legal now says what cannot be scrubbed from memory. The vault key is a non-extractable CryptoKey, so its bytes never reach our code. The passphrase is an ordinary JavaScript string from a text field, and strings are immutable — no page can overwrite one, so it persists until the garbage collector reclaims it. We hold it as briefly as possible and never store it, but that is the honest limit, and a web password manager claiming otherwise is describing an intention.
  • The clipboard timer now covers the vault — copying a password, a username or a security answer from an entry arms the same wipe the generator uses. It was extracted from main.js into a shared module rather than duplicated.
  • Staying unlocked between pages, with the cost stated. Walking from the generator to the vault inside the lock window no longer asks for the passphrase again. Making that work writes the vault key to browser storage, wrapped under a second key the browser holds — for the length of the window, a slightly weaker position than "the key exists only in memory". Setting the vault lock to Never switches it off entirely, and the Legal and Docs pages both say what the trade is. An earlier SharedWorker approach was measured, found to die with the last document, and dropped.

Patch
All randomness now drawn from crypto.getRandomValues()
Every generator drew its random values from Math.random(), which is not cryptographically secure — passwords produced before this release should be considered predictable and are worth regenerating.
Security
  • Predictable passwords — all 22 randomness call sites used Math.random(), which V8 implements as xorshift128+. Its internal state can be recovered from a short run of observed outputs, meaning an attacker who saw some generated passwords could predict others. All seven generators (Simple, Advanced, Words, Passphrase, Wireless, Mad Lib, Numbers) were affected.
  • New randInt() helper — draws a uint32 from crypto.getRandomValues() and uses rejection sampling to stay unbiased: draws at or above the largest multiple of the range that fits in a uint32 are discarded, so the remaining values divide evenly. A plain % n would have skewed results toward low values. The randPick, randBool, and randChar helpers wrap it, and every call site now routes through them — including the Fisher-Yates shuffle in Advanced mode.
  • No silent fallback — crypto.getRandomValues() requires a secure context (HTTPS or localhost). Generation now fails loudly rather than falling back to Math.random(), which would quietly reintroduce the same weakness.
